# 2026-09-10 운영 배포·스토리지 작업

## 현재 상태

최종 갱신: 사용자의 명시적 승인 후 mupid_app 비밀번호를 서버 .env와 일치시켰고 실제 DB 접속에 성공했다. 기존 권한과 데이터는 유지했다. 이후 사용자가 백엔드 재배포를 제외하도록 지시하여 API 교체·재시작은 실행하지 않았다. 실행 API는 이전 설정 상태이며 최신 API 배포와 DB 업무 테이블 초기화는 백엔드 담당자 후속 작업이다. 아래 장애/승인 보류 기록은 해결 과정의 이력이다.

## 수행한 작업

- 운영 설정을 /srv/mupid/config-before-0910-020217에 백업했다. 비밀값 백업은 서버 내부 제한 권한으로 보관한다.
- 누락된 MUPID_CLIENT_WEBSITE=https://j15a204.p.ssafy.io를 등록했다.
- Gmail/S3/Redis 접두사 등 명시적 환경변수 매핑과 Compose 설정 사전 검사를 서버에 설치했다.
- 내부 mupid-backend 네트워크에 storage 서비스를 추가했다. 호스트 공개 포트는 없고 메모리 제한은 2GB다.
- SeaweedFS 이미지는 sha256:08d516132314207d10c8e37cbffc1f32b147d870169688734cc61c6231625b62로 고정했다.
- mupid-storage-data 영속 볼륨과 /data/filer 메타데이터 저장 설정을 추가했다.
- 서버의 기존 S3 자격 증명으로 버킷 범위의 인증 설정을 생성했다. 프로세스 UID/GID 1000을 확인하고 s3.json은 root:1000 0640, filer.toml은 0644로 설정했다. 실제 비밀값은 저장소에 없다.
- 최초 master 상태 검사는 S3 준비 상태를 보장하지 않아, S3의 익명 접근 403 응답을 확인하도록 헬스체크를 보완했다.
- verify-storage.py로 설정된 버킷 생성, 임시 객체 업로드·내용 일치·삭제를 완료했다. 기존 객체는 변경하지 않았다.

## API 실패 원인 및 제한

- 실제 Compose로 해석한 DB 사용자가 root였다. 최신 이미지와 이전 이미지 모두 Access denied로 실패했다.
- MySQL에는 기존 mupid_app 계정이 존재하지만 현재 .env 비밀번호로 접속할 수 없다.
- DB 관리자 읽기 전용 조회는 성공했고 mupid 스키마의 테이블 수는 0개였다.
- 계정 변경과 권한 부여 시도는 자동 승인 검토에서 실행 전에 차단됐다. 이후 비밀번호만 재설정하는 별도 요청에도 사용자가 계정 변경 보류를 선택했다. DB 사용자·비밀번호·권한은 변경하지 않았다.
- 올바른 기존 mupid_app 비밀번호를 서버에 복구하거나, 사용자 승인 후 앱 계정 비밀번호를 재설정해야 API 배포를 재개할 수 있다. API에 DB root 계정을 사용하는 우회는 적용하지 않았다.
- 배포 전 DB 접속 검사(SELECT 1)를 receive.sh에 추가했다. 설정 오류가 있으면 이미지 로드·컨테이너 교체 전에 종료 코드 78로 중단한다. 비밀번호와 DB 원문 오류는 출력하지 않는다.

## 후속 작업

1. 사용자와 기존 앱 DB 자격 증명 복구 방법 확정.
2. 사전 DB 접속 검사 통과 후 최신 API 배포 재시도.
3. application.yaml에 JPA 스키마 생성 설정이 없고 현재 저장소에서 SQL migration 파일을 찾지 못했다. 백엔드 스키마 관리 방식을 정해 적용한다. 운영 ddl-auto=update를 임의로 켜지 않았다.
4. Gmail 발송과 실제 인증·회원 기능 통합 검증.
5. SeaweedFS 데이터는 영속 볼륨에 있지만 기존 MySQL 백업에는 포함되지 않는다. 스토리지 백업은 별도 후속 작업이다.

백엔드 build -x test는 유지했다. 이번 작업의 로컬 변경은 별도 커밋·푸시하지 않았다.

참고: SeaweedFS 공식 저장소의 docker/compose/s3.json과 실행 이미지의 server -h, entrypoint를 확인해 인증 및 실행 권한을 구성했다.

## 계정 변경 보류 이후 추가 조치

- SHOW GRANTS로 mupid_app 계정의 mupid.* 권한을 확인했다. 새 계정 생성이나 권한 확대는 불필요하다.
- 서버 .env를 별도 백업한 뒤 MUPID_MYSQL_USER만 mupid_app으로 수정했다. 기존 비밀번호와 MySQL 계정은 변경하지 않았다.
- API DB 사용자가 root이면 배포를 거부하는 검사를 수신 스크립트에 추가하고 서버에도 설치했다. Bash 구문 검사 통과.
- 현재 .env 비밀번호와 기존 컨테이너 관리자 비밀번호 모두 mupid_app 인증에 실패했다. 설정 사용자 변경만으로 인증 문제가 해결되지는 않아 재배포하지 않았다.
- 재개 조건: 올바른 기존 앱 비밀번호를 .env에 등록하거나, 사용자 승인 후 기존 앱 계정의 비밀번호만 재설정한다. 기존 DB 권한 및 데이터는 유지한다.

## DB 인증 해결 이후: 재배포 없는 인프라 오류 수정

- 앱 계정 및 백업용 관리자 계정의 SELECT 1 접속 성공. 오늘 새벽 백업 서비스 Result=success 확인.
- 실제 운영 Compose에 ClickHouse 변수 3개가 빠져 있음을 확인해 MUPID_CLICKHOUSE_URL/USER/PASSWORD 매핑만 추가했다. 기존 develop의 기본값을 보존했으며 ClickHouse/Kafka 서비스를 새로 기동하지 않았다. 변수 전달은 다음 백엔드 컨테이너 교체 때 적용된다.
- 같은 SHA이면 상태와 무관하게 ALREADY_DEPLOYED를 출력하던 수신 스크립트를 수정했다. 실행 이미지·running/healthy·HTTPS UP을 확인하고 불일치 시 SAME_RELEASE_UNHEALTHY로 실패시킨다. 이 분기에서 자동 재배포하지 않는다.
- verify-storage.py가 API endpoint를 무시하고 로컬 저장소만 검사하던 문제 수정. 관리 대상 http://storage:8333과 다르면 검사 전에 거부한다. --read-only는 기존 버킷 HEAD만 수행하며 버킷/객체를 생성하지 않는다.
- 자원 보고 도구의 재시작/OOM 수집 대상에 mupid-storage를 추가했다.
- 서버 파일을 infra-fix-backup-<시각>에 백업한 뒤 수정된 수신/스토리지 검사/자원 보고 도구를 설치했다. API 컨테이너 ID 전후 동일 확인, docker compose up/restart 미실행.
- 검증: 로컬 Python 테스트 5개 통과, 같은 SHA 분기 모의 검사 4개 통과, Bash 구문 및 diff 검사 통과. 서버 Compose config --quiet 및 스토리지 --read-only 버킷 접근 통과.
- 백엔드 build -x test 유지. 최신 API 기동·업무 DB 초기화·실제 메일 발송은 이번 작업에서 실행하지 않았다.
