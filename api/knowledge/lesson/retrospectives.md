# 회고에서 남길 것

주간 회고(`회고/YYYY-MM-DD.md`)에서 **반복해서 나왔거나 실제로 무언가를 바꾼 것**만 추린다. 회고 원문은 그대로 두고, 여기에는 결론만 남긴다.

## 반복해서 나온 문제

같은 말이 여러 사람에게서, 또는 두 주 연속 나온 것들이다.

### 기술이 아니라 문제에서 시작하기

- 이규원(08-28): *"기능을 생각할 때 서비스의 핵심 문제와 차별점보다 **구현하고 싶은 기술이나 기능을 먼저** 생각하는 경우가 있었다"*
- 정예준(08-28): *"**오버 엔지니어링을 줄이고** 핵심 기능에 집중하자"*
- 김건우·정준호(08-28): 차별점을 설정하지 못했다

→ **새 기술을 도입할 때 [ADR](../decision/README.md) 을 쓴다.** 맥락(무슨 문제를 푸는가)을 못 쓰겠으면 도입하지 않는다.

### 아이디어 고착과 재탐색 비용

- 이규원(08-28): *"아이디어가 여러 번 변경되면서 하나의 주제를 깊게 검토하기보다 새로운 아이디어를 찾는 데 많은 시간이 사용되었다"*
- 김건우(08-28): *"기존 서비스와의 차별점이 체감되지 않는 문제 / 아이디어 고착화"*

→ 되돌리기 어려운 결정은 ADR 로 고정한다. 재논의하려면 새 ADR 을 쓴다.

### 자동화가 조용히 틀린 데이터를 만든다

- 김건우(09-04): *"비동기 렌더링과 DOM 변경으로 **잘못된 음원이 저장되는** 문제가 발생했다"*
- Try: *"자동화는 **소규모 배치 단위**로 실행하고 오류 발생 시 즉시 검수한다"*

→ 수집·적재 자동화는 전량 실행 전에 소규모로 돌리고 결과를 눈으로 본다. 실패보다 **조용히 잘못된 데이터**가 더 비싸다.

### 발표·기획에 밀려 인프라가 뒤로 간다

- 김건우(09-04): *"발표 준비에 집중하면서 인프라 구축 진도가 상대적으로 부족했다"*

→ 데모 일정이 있는 주에는 인프라 작업을 먼저 잡는다.
