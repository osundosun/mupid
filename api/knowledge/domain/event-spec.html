청취 이벤트 22종 명세

사용자가 음악을 들을 때 남기는 행동 22종의 필드, 값 집합, 그리고 각 이벤트가 어떤 파생 신호로 이어지는지 정리한다. 수집 단계는 원시 신호만 남긴다 — 가중치와 분류는 분석 시점에 계산한다.

frontend/lib/analytics→ POST /api/v1/events→ Kafka mupid.listen.events→ listen_events→ 파생 3종

값 검증은 수집기가 한다. 값 집합만 어긋난 경우 그 칸만 비우고 이벤트는 받는다. ClickHouse CONSTRAINT 로 막지 않는 이유는, 한 건이 어긋나면 블록 전체가 거부돼 Kafka 소비가 멈추기 때문이다.

하트비트가 구간 경계에서 쪼개지는 방식

스킵 해석 — 수집과 분류가 나뉜다

프론트는 무엇으로 넘겼는지와 언제 넘겼는지만 보낸다. “이 사용자가 이 구간을 전에 들었는지” 도, 구간 경계가 어디인지도 프론트는 모르기 때문이다. 분류는 v_track_skips 가 쿼리 시점에 만든다 — 일반 VIEW 라 기준을 고치면 과거 이벤트까지 새 기준으로 다시 해석된다.

부정 판정을 추천으로 들어온 경우에만 강하게 준다. 사용자가 직접 검색해 튼 곡을 넘긴 것에 같은 점수를 주면 추천 평가가 왜곡된다.

프론트가 지켜야 할 것

  1. 매번 재생기에서 위치를 실제로 읽어서 position_ms 를 만든다. 화면이 들고 있던 값을 쓰면 백그라운드 탭에서 틀어진다.
  2. 구간 번호를 보내지 않는다. 밀리초만 보내고 구간 매핑은 백엔드가 한다.
  3. occurred_at 은 이벤트가 생긴 그 순간 각인한다. 배치로 묶여 늦게 나가도 각 이벤트는 자기 시각을 들고 간다.
  4. entry_path 를 재생의 모든 이벤트에 싣는다. 스킵 해석과 커버리지가 진입 경로를 필요로 하는데, 그때마다 PLAY_START 로 되짚는 JOIN 을 두지 않기 위해서다.
  5. 가중치도 분류도 계산하지 않는다. 원시 신호만 남기고 해석은 분석 시점에 한다.

이 규칙은 frontend/lib/analytics/ 가 지킨다. 화면에서 fetch 를 직접 부르지 말고 이 모듈을 쓴다.

알려진 함정

구간 지정 이벤트는 position_ms 를 함께 보내야 한다

구간 매핑이 position_ms 한 점으로 이뤄지고 position_ms > 0 을 요구한다. 범위만 보내면 조건에 걸려 가장 강한 긍정 신호(+1.5)가 조용히 사라진다. 라이브러리가 position_ms = start_ms 를 자동으로 넣는다. 지정 범위가 여러 구간에 걸치면 시작점이 속한 구간 하나만 잡힌다.

PLAYLIST_REMOVE 의 −0.8 은 지금 발동하지 않는다

신호 목록에는 들어 있지만 이 행동에는 재생 위치라는 것이 없어 position_ms 가 0 이고, 같은 조건에 걸린다. 플레이리스트에서 빼는 행동은 애초에 구간 신호가 아니라 곡 신호라 이 자리가 맞지 않는다.

중복은 Kafka 에 넣기 전에 걸러야 한다

원본 테이블은 같은 event_id 를 병합으로 정리하지만, 파생 뷰는 INSERT 시점에 이미 발화한 뒤다. 중복 LIKE 하나가 가중치를 +1.0 이 아니라 +2.0 으로 만들고 병합으로도 사라지지 않는다. 그래서 수집기가 Redis 로 event_id 를 먼저 거른다.
