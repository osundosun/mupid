# MuBTI 판정 명세

MuBTI 네 축을 **무엇으로, 어떻게** 판정하는지만 짧게 정리한다.
설계 배경·적재·API 계약은 [mubti-report.md](mubti-report.md), 결정 이유는
[decision/0019](../decision/0019-report-reads-clickhouse-directly.md).

구현은 `api/report/service/MubtiScorer.java` 한 파일이다. **계수는 전부 거기 상수로만
있다.** 조회할 때마다 계산하고 점수는 저장하지 않는다 ([decision/0015](../decision/0015-derive-interpretation-at-query-time.md)).

---

## 네 축 한눈에

| 축 | 양수 | 음수 | 핵심 지표 |
|---|---|---|---|
| **A** | `V` 보컬파 | `I` 멜로디파 | 보컬곡 청취 비중의 **카탈로그 기준선 대비 편차** |
| **B** | `M` 매니아형 | `T` 트렌드형 | 아티스트 집중도(HHI) vs 재생수 백분위·신곡 비중 |
| **C** | `F` 완주형 | `S` 스킵형 | `PLAY_END` / (`PLAY_END`+`TRACK_SKIP`), 앞으로감기 빈도 |
| **D** | `E` 개척형 | `C` 국밥형 | **탐색량과 반복량을 각각 절대량으로** 재고 뺀다 |

점수는 −1~+1. 부호가 글자를 정한다.

## 쓰는 지표와 출처

| 지표 | 어디서 | 쓰는 축 |
|---|---|---|
| 곡별 청취 ms | ClickHouse `PLAY_PROGRESS` | 트리맵 · A · B |
| 곡별 재생 시도 수 | ClickHouse `PLAY_START` | **D** |
| `PLAY_END` · `TRACK_SKIP` · `SEEK_FORWARD` 수 | ClickHouse | C |
| 최근 3일 들은 곡 | ClickHouse | D |
| 보관함 곡 (좋아요 + 플리 수록곡) | MySQL `music_reactions` · `playlist_tracks` | D |
| `has_vocal` | MySQL `music_analysis` | A |
| 아티스트 · `release_date` | MySQL `music` 외 | B |
| **곡별 누적 재생수 (카탈로그 대중성)** | **ClickHouse** `PLAY_START`, 전 사용자·전 기간 | B |

> ⚠ **청취 ms 와 재생 시도는 집합이 다르다.** 하트비트가 5초 간격이라 **그 전에 넘긴
> 곡은 청취 ms 가 0 이고 집계에 행 자체가 없다.** 실측으로 재생 시도 28회 중 22회가
> 청취 0 이었다. 그래서 D축은 시간이 아니라 재생 시도를 센다.

## ClickHouse 쿼리

전부 `analytics/repository/ListenAnalyticsRepository.java` 에 있다. 공통 규칙 셋:

1. **Distributed 테이블(`listen_events`)을 읽는다** — Kafka 적재가 샤딩 키를 안 타서
   한 사용자 이벤트가 두 샤드에 흩어져 있다.
2. **`GROUP BY event_id` 로 감싼다** — `ReplacingMergeTree` 중복 제거는 병합 시점이라
   그 전에는 같은 이벤트가 여러 행이다.
3. **시각은 문자열 + `toDateTime64(?, 3, 'Asia/Seoul')`** — 드라이버 시간대에 결과가
   좌우되면 안 된다.

| 메서드 | 내용 | 쓰는 곳 |
|---|---|---|
| `trackListening` | `PLAY_PROGRESS` 의 `sum(position_ms − from_ms)` 를 곡별로 | 트리맵 · A · B |
| `playSummary` | 하루 이벤트 종류별 개수 + `uniqExact(play_id)` | C |
| `playStartsByTrack` | `PLAY_START` 를 곡별로 count (하루, 한 사용자) | **D** |
| `tracksHeardBefore` | 그날 이전 N일 동안 만진 곡 번호 (`DISTINCT`) | D |
| `catalogPlayCounts` | `PLAY_START` 를 곡별로 count (**전 기간·전 사용자**) | **B** |
| `activeUsers` | 그날 이벤트를 남긴 사용자 | 자정 배치 |

`catalogPlayCounts` 만 사용자·날짜 필터가 없다. 그래서 호출부(`CatalogBaseline`)가
1시간 캐시하고, 그 안에서 **한 번도 재생되지 않은 곡 수만큼 0 을 채운다** — 재생 로그에는
재생된 곡만 나오므로 그대로 쓰면 분모가 작아져 백분위가 통째로 뒤집힌다.

> 서브쿼리 집계 별칭을 컬럼명과 같게 쓰면 안 된다(`any(track_id) AS track_id`).
> ClickHouse 가 바깥 조건을 서브쿼리 WHERE 로 밀어 넣으며 부딪혀 `ILLEGAL_AGGREGATION`
> (184) 으로 실패한다. `AS tid` 처럼 겹치지 않게 쓴다.

## 축별 공식과 의도

### A — 보컬(V) / 멜로디(I)

```
score_A = clamp((내 보컬곡 청취 비중 − 카탈로그 보컬곡 비중) × 2.5)
```

**절대 비중을 쓰면 안 된다.** 카탈로그의 90%가 보컬곡이면 모두가 V 가 되어 축이 죽는다.
분석 행이 없는 곡은 분자·분모 양쪽에서 빠진다 — `has_vocal` 없음을 `false` 로 읽으면
분석이 덜 된 카탈로그에서 모두가 멜로디파가 된다.

**가장 약한 축이다.** `has_vocal` 은 곡의 속성이지 듣는 방식이 아니다. "후렴만 되감아
듣는가" 를 보려면 구간별 청취량이 필요한데 `track_sections` 를 채우는 파이프라인이 없다.

### B — 트렌드(T) / 매니아(M)

```
score_B = 0.55×(집중도×2−1) − 0.30×(대중성백분위×2−1) − 0.15×(신곡비중×2−1)
```

- **집중도**: 아티스트별 청취 시간 점유율의 허핀달 지수. 아티스트가 적으면 자동으로
  높아지므로 `(HHI − 1/n)/(1 − 1/n)` 로 정규화한다.
- **대중성**: **ClickHouse 재생 로그 기준** 카탈로그 백분위, 청취 시간 가중 평균.
- **신곡**: `release_date` 90일 이내 곡의 청취 비중.

> **대중성을 `music.play_count` 로 재지 않는다.** 그 컬럼을 올리는 코드가 저장소에
> 없어 전 곡이 0 이고, 정렬 배열이 전부 0 이면 백분위가 상수가 되어 **가중치 0.30 짜리
> 항이 아무도 구분하지 못하는 오프셋으로 전락한다.** 실제 재생 로그(`PLAY_START`)를
> 세면 컬럼보다 정확하고, `track_id` 만 쓰므로 곡 메타데이터를 ClickHouse 에 복제할
> 필요도 없다.
>
> 백분위는 **"나보다 적게 재생된 곡의 비율"**(동점 구간의 왼쪽 끝)이다.
> `Collections.binarySearch` 는 동점에서 아무 자리나 돌려주므로 쓰면 안 된다 — 재생 0 인
> 곡이 대부분인 카탈로그에서 그 값이 0 이 아니라 0 무리의 한가운데가 되어, **아무도 안
> 들은 곡이 "중간쯤 인기" 로 읽힌다.**

### C — 완주(F) / 스킵(S)

```
완주율   = PLAY_END / (PLAY_END + TRACK_SKIP)
앞감기율 = SEEK_FORWARD / 재생 수
score_C = clamp(0.7×(완주율×2−1) − 0.3×clamp(앞감기율/2))
```

가장 깨끗하게 이벤트로 떨어지는 축이다. `PLAYBACK_ABANDON`(앱이 닫혀 끊김)과
`PLAY_ERROR` 는 세지 않는다 — 의도한 스킵이 아닌 것을 스킵으로 세면 네트워크가 나쁜
사용자가 전부 스킵형이 된다.

> ⚠ 다만 실측에서 재생 28회 중 END 2 · SKIP 1 · ABANDON 18 이었다. **판정 근거가
> 28번 중 3번뿐**이라는 뜻이다.

### D — 국밥(C) / 개척(E)

```
explore = clamp(그날 처음 만진 곡 수 / 8)
comfort = clamp((익숙한 곡의 평균 재생 횟수 − 1) / 2)
score_D = clamp(explore × 1.2 − comfort × 0.5)
```

- **처음 만진 곡** = 그날 `PLAY_START` 한 곡 중 최근 3일 기록에도, 보관함에도 없는 곡.
  **스킵으로 끝난 재생도 센다.**
- **익숙한 곡** = 최근 3일 안에 들었거나 좋아요·플레이리스트에 담아 둔 곡.

**의도 세 가지가 이 식에 박혀 있다.**

| 의도 | 어떻게 반영했나 |
|---|---|
| 보관함에 넣어 둔 걸 반복하면 국밥형 | 좋아요·플리 수록곡을 "익숙한 곡" 에 넣고 반복 횟수를 잰다 |
| 빠르게 넘기며 디깅해도 탐색으로 친다 | 청취 시간이 아니라 `PLAY_START` 를 센다 |
| **둘 다 많으면 개척형** | 비율이 아니라 절대량으로 각각 재고, `1.2 > 0.5` 로 탐색에 더 큰 계수 |

마지막이 핵심이다. 비율(새 곡 / 전체)로 재면 두 행동이 서로의 분모가 되어 깎아 먹으므로
**"플리를 계속 돌리면서 동시에 새 곡도 활발히 디깅하는 사람" 을 표현할 수 없다.**

| 케이스 | explore | comfort | score | 결과 |
|---|---|---|---|---|
| 새 곡 10개 디깅 + 플리 3곡 4회씩 | 1.0 | 1.0 | +0.70 | **E** |
| 새 곡 0, 플리만 반복 | 0 | 1.0 | −0.50 | C |
| 새 곡만 8개 | 1.0 | 0 | +1.00 | E |
| 새 곡 2개, 플리 반복 많음 | 0.25 | 1.0 | −0.20 | C |

## 판정을 흔들지 않기 위한 두 장치

**표본 하한.** 하루 청취가 5분 미만이거나 서로 다른 곡이 3곡 미만이면 판정하지 않는다.
`mubti: null` + `sample.sufficient: false` 로 내려간다. 아침에 두 곡 듣고 "당신은
스킵형" 이라고 단정하면 판정 자체를 못 믿게 된다.

**이력 현상.** 한 번 정해진 글자는 반대편 점수가 **0.15 를 넘어서야** 바뀐다. 직전
판정은 Redis 에 하루치로 둔다. 이게 없으면 곡 하나 스킵할 때마다 `F` 와 `S` 가 번갈아
나오고, 실시간 갱신 화면에서 그 깜빡임은 곧 "이 판정은 의미 없다" 로 읽힌다.

`confidence` 는 그 축의 근거량이다. **0 이면 근거가 없어 기본값으로 둔 축**이다.

## 지금 약한 곳

| | 무엇이 문제인가 |
|---|---|
| A축 | `music_analysis` 가 채워진 곡이 적어 `confidence` 가 낮다. 구간 신호가 없어 "듣는 방식" 을 못 본다 |
| B축 | `play_count` 가 전부 0 이라 대중성 차원이 죽고 상수 편향만 남는다 |
| C축 | 종료의 대부분이 `PLAYBACK_ABANDON` 이라 판정 근거가 얇다 |
| 공통 | `track_sections` 를 채우는 파이프라인이 없어 구간 기반 신호 전부가 빈 결과 |

계수는 **실제 사용자 분포로 조율한 값이 아니다.** 축의 뜻에서 역산한 출발점이다.
한쪽으로 쏠리면 `MubtiScorer` 의 상수만 고치면 되고, 저장된 점수가 없으므로 과거까지
새 기준으로 다시 읽힌다. 규칙을 바꿀 때 무엇이 깨지는지는
`api/src/test/.../report/MubtiScorerTest.java` 가 지킨다.
