# 0021. 자연어는 대화 모델이 조건으로 바꾼다 — 별도 해석기를 세우지 않는다

**상태** 채택 · 2026-09-23 보완 — 어휘와 게이트 조건을 Spring 이 만든다 · 2026-09-25 보완 — 게이트 조건은 추천 서버로 되돌아간다

> **2026-09-25 (S15P21A204-458, 계약 v3).** 추천 서버가 곡·구간 값을 ClickHouse 피처 저장소에서
> 직접 읽게 되면서 `catalog` 본문과 `QueryPlanFilter` 를 걷어냈다. 게이트 조건은 추천 서버가
> 건다 — 규칙을 두 곳에 두지 않으려는 것이다(`infra/VECTOR-STORE-DESIGN.md` §9.4). 어휘는 그대로
> `RecommenderFacets` 가 MySQL 로 만든다. "어휘 먼저, 없는 조건은 결과 0" 도 그대로다 — 추천 서버가
> 어휘에 없는 필수 조건을 `UNSATISFIABLE_CONDITIONS`(404)로 답하고 Spring 은 빈 결과로 받는다.

> **2026-09-23 (S15P21A204-423).** 아래의 `GET /internal/facets` 는 없앴다. 추천 서버가
> Spring 을 부르지 않게 되면서(연동 계약 2026-09-23 절) 후보가 Spring 에 있으므로, 어휘는
> `RecommenderFacets` 가 MySQL 후보에서 만들고 게이트 조건은 `QueryPlanFilter` 가 걸어
> 남은 후보만 `catalog` 로 보낸다. "어휘 먼저, 없는 조건은 결과 0" 이라는 결정은 그대로다.

## 맥락

채팅 화면의 곡 추천을 목업에서 실제 추천으로 바꾸려면, 사용자가 한 말("조용한 피아노 음악")을 추천기가 쓸 수 있는 조건으로 옮겨야 한다. 추천 서버(`ai_server/`)의 `/internal/recommendations/search` 는 원문을 받을 수 있지만, 받으면 **별도의 자연어 해석기를 HTTP 로 부른다.** 그 해석기는 Qwen 과 CLAP 을 GPU 에 올려 쓰는 구성이라 **GPU 서버가 하나 더 필요하다.** 지금 그 서버는 없고, 그래서 `search` 는 501 을 돌려주고 있었다.

그런데 우리에게는 이미 LLM 이 하나 있다. 채팅이 쓰는 대화 모델이다. 자연어를 구조화된 조건으로 옮기는 일은 그 모델이 가장 잘 하는 일이기도 하다.

## 결정

**조건 추출은 대화 모델이 한다.** 추천 서버에는 원문(`query`) 대신 이미 만들어진 조건(`query_plan`)을 보낸다.

```
사용자 발화
  → GET /internal/facets        카탈로그에 실제로 있는 태그 어휘를 받는다
  → 대화 모델의 툴 호출          그 어휘 안에서 filters / exclude 를 고른다
  → POST /internal/recommendations/search { "query_plan": { ... } }
```

어휘를 먼저 받아 오는 것이 핵심이다. 모델에게 자유롭게 태그를 짓게 하면 카탈로그에 없는 말이 나오고, 그러면 조건을 만족하는 곡이 0 이 된다. 툴 스키마의 `enum` 을 `/internal/facets` 로 채워 **고를 수 있는 값만 보여 준다.**

조건을 하나도 못 뽑았으면 `search` 가 아니라 `next` 를 부른다. 조건 없는 `search` 는 추천 서버가 400 으로 거부한다 — "검색했는데 조건이 안 걸린 결과" 를 막으려고 일부러 그렇게 되어 있다.

## 결과

- **GPU 서버를 추가로 세우지 않아도 채팅에서 실제 추천이 나온다.** 장르·언어·보컬·악기·구간 유형은 하드 필터로 걸린다.
- 모델이 어휘 밖의 말을 만들어도 조건이 조용히 무시되지 않는다. 추천 서버가 "만족시킬 수 없음" 으로 보고 결과 0 을 준다.
- **CLAP 임베딩 기반의 의미 재정렬은 빠진다.** "여운이 길다" 처럼 태그로 떨어지지 않는 느낌은 순위에 반영되지 않는다. 무드는 추천 서버가 태그 일치로 부드럽게 재정렬해(`MOOD_WEIGHT`) 그 자리를 일부 메운다.
- 왕복이 하나 늘었다. 어휘는 카탈로그가 기동 후 바뀌지 않으므로 한 번만 받아 재사용한다.
- 해석기를 나중에 세우면 `query` 를 보내는 쪽으로 갈아탈 수 있다. 추천 서버는 두 경로를 모두 받는다.

## 실패했을 때

추천이 안 된다고 **대화까지 끊지 않는다.** 추천 서버가 죽었거나 주소가 설정되지 않았으면 툴 결과에 "지금은 곡을 찾을 수 없다" 를 담아 모델에게 돌려준다. 모델이 그 사실을 말로 풀어 답한다. 여기서 502 를 올리면 사용자는 빈 화면만 본다.

조건에 맞는 곡이 없는 것(`NO_CANDIDATES`)은 **장애가 아니다.** 빈 목록으로 다루고 재시도하지 않는다. 재시도는 `500` · `503` · 타임아웃에만 한 번이다 — 읽기 타임아웃이 5 초라 두 번이면 최악 10 초를 기다리는데, 그 앞에서 이미 대화 모델을 기다린 뒤다.
