# 0026. 파형은 배치가 미리 계산하고, 기기 계산은 폴백으로 남긴다

**상태** 채택 (2026-09-22 · S15P21A204-420)

## 맥락

화면의 탐색 막대는 곡의 **진폭 포락선**(파형)을 그린다. 지금까지 이 값은
[`frontend/lib/track-waveform.ts`](../../../frontend/lib/track-waveform.ts) 가
기기에서 만들었다. 곡을 열 때마다

1. 스트림 목록을 받고 → 2. 청크 목록을 받고 → 3. **청크를 전부 내려받아**
→ 4. Opus 로 풀어 → 5. 160칸 RMS 를 세어 → 6. 최댓값으로 나눈다.

파일 머리말이 "서버 파형·배포 JSON·이전 세션의 저장된 파형은 사용하지 않는다"
라고 못 박고 있었다. 그 규칙이 지켜 준 것이 있다 — **화면에 보이는 파형이 실제로
재생되는 바이트에서 나온다.** 서버가 준 숫자가 낡았을 가능성이 없다.

대가는 크다. 파형은 **곡이 바뀌지 않는 한 같은 값**인데, 사람 수 × 재생 횟수만큼
다시 계산한다. 곡 하나에 청크가 수십 개, 합쳐서 수 MB 다. 모바일 회선에서는
파형이 그려지기까지 곡 전체를 받아야 한다.

## 결정

**배치가 청킹할 때 원본에서 파형을 뽑아 서버에 올리고, 화면은 그것을 먼저 쓴다.
없으면 예전 경로로 내려간다.**

| | 어디 |
|---|---|
| 계산 | `music_preprocessing/waveform.py` — ffmpeg 로 8kHz 모노 PCM → 칸별 RMS → 최댓값으로 나눔 |
| 등록 | `PUT /api/v1/music/{musicId}/waveform` (`@SystemRole`) |
| 보관 | 오브젝트 스토리지 `music/{musicId}/waveform.json` + `music.waveform_file_id` |
| 조회 | `GET /api/v1/music/{musicId}/waveform` (로그인한 누구나) |
| 폴백 | 404 면 `track-waveform.ts` 가 예전처럼 청크를 풀어 계산 |

### 폴백을 남긴 것이 이 결정의 핵심이다

서버 파형은 **있으면 좋은 것**이지 전제가 아니다. 파형이 하나도 올라가지 않은
상태에서도 화면은 이 변경 전과 똑같이 돈다. 그래서

- 카탈로그 1060곡을 미리 채우지 않아도 배포할 수 있다.
- 배치가 파형 등록에 실패해도 **스트림을 되돌리지 않는다.** 재생에 지장이 없는
  것 때문에 곡을 통째로 다시 올리는 쪽이 손해다.
- 로컬 데모 음원(`track.localAudio`)은 애초에 서버에 곡이 없어 그대로 간다.

대신 "보이는 파형이 재생되는 바이트에서 나온다" 는 보장을 잃는다. 음원을 갈아
끼우고 파형을 다시 올리지 않으면 **옛 파형이 남는다.** 지금은 `batch` 가 재청킹할
때 파형도 같이 올리므로 한 경로로 묶여 있다 — 그 순서가 깨지면 이 위험이 살아난다.

## 고른 것과 버린 것

| | 방법 | 판단 |
|---|---|---|
| A | 지금처럼 기기에서만 계산 | 곡마다 수 MB. 요구가 여기서 출발했다 |
| B | **스프링이 청크를 풀어 계산해 캐시** | 서버에 Opus 디코더를 들여야 한다. 배치에는 이미 ffmpeg 가 있다 |
| C | **배치가 계산해 서버가 보관** | 채택 |

### B 를 버린 이유

계산 자체는 한 번만 하면 된다는 점에서 C 와 같다. 다른 것은 **누가 디코더를
들고 있느냐**다. 배치는 이미 ffmpeg 로 Opus 인코딩을 하고 있어서 같은 도구로
PCM 을 한 번 더 받으면 끝이고, 원본 파일이 손 닿는 곳에 있다. 스프링이 하려면
JVM 용 Opus 디코더를 새로 들이고, 이미 올라간 청크를 스토리지에서 다시 받아
풀어야 한다 — 파형 하나 때문에 서버가 음원 처리 책임을 갖게 된다.

## 왜 청크처럼 nginx 로 우회하지 않는가

청크 업로드·다운로드는 스프링을 거치지 않는다 (`auth_request` + `X-Accel-Redirect`,
[0008](0008-deploy-image-from-infra.md) 의 배포 구조 안에서). 곡당 100KB 짜리가
수십 개라 바이트가 JVM 힙을 지나가면 안 되기 때문이다.

**파형은 곡당 1~2KB 다.** 같은 길을 깔려면 개발·운영 nginx 설정 양쪽에 location 과
auth_request 를 새로 넣고 배포까지 해야 하는데, 얻는 것이 없다. 이미 있는
`StorageService` 로 스프링이 직접 읽고 쓴다.

## 왜 `music` 에 참조 컬럼을 두는가

키가 곡 번호에서 그대로 만들어지므로(`music/{musicId}/waveform.json`) 컬럼 없이
`getFileByKey` 로 찾을 수도 있었다. 한 번 그렇게 정했다가 되돌렸다.

1. **이 스키마의 파일 참조는 전부 FK 컬럼이다** — `albums`·`artists`·`music`·
   `users`·`mubti` 의 `image_file_id`, `chunks.file_id`. 파형만 규칙으로 찾으면
   `music` 을 봐도 이 곡에 파형이 있는지 알 수 없다.
2. **백필이 대상을 SQL 로 뽑아야 한다** — `WHERE waveform_file_id IS NULL`.
3. **`storage_object_key` 에 인덱스가 없다** (`PRIMARY` 뿐). 청크 때문에 행이
   곡당 수십 개씩 쌓이는 테이블이라 조회마다 풀스캔이 된다.

스키마 변경 내역은 [domain/erd.md](../domain/erd.md) 의 "2026-09-22 — 파형".

## 저장 형식을 전역 Jackson 설정에 묶지 않는다

파일 안의 필드 이름은 `WaveformFile` 이 `@JsonProperty` 로 직접 적고, 서비스는
주입받은 매퍼가 아니라 자기 `ObjectMapper` 를 쓴다. `spring.jackson.
property-naming-strategy` 는 **응답**의 규약이라, 그것에 기대면 누가 그 설정을
바꾸는 순간 이미 스토리지에 올라간 파형을 못 읽는다. Redis 의 재생 큐 문서가
같은 이유로 전역 매퍼를 쓰지 않는다 (`PlayQueueRepository`).

덧붙여 Spring Boot 4 의 자동설정은 **Jackson 3 만 빈으로 등록**해서
`com.fasterxml` 의 `ObjectMapper` 빈이 애초에 없다. 주입받으려 하면 컨텍스트가
뜨지 않는다.

## 값이 없는 곡은 빈 배열이 아니라 404 다

가사(`GET …/lyric`)는 가사가 없어도 200 에 빈 목록을 준다 — 곡은 있는데 가사만
없는 것이 오류가 아니기 때문이다. 파형은 반대로 **404** 다.

빈 배열을 주면 받는 쪽이 "없다" 와 "평평하다" 를 구분할 수 없고, 그러면 폴백
분기를 만들 수 없다. 화면은 파형이 없을 때 **다른 일을 해야 한다.**

같은 이유로 등록 쪽은 **값이 전부 0 인 배열을 400 으로 거절**한다. 계산이 실패한
배치가 올린 것으로 보는데, 받아 두면 화면이 폴백하지 않고 평평한 선을 그려서
고장이 고장처럼 보이지 않게 된다.

## 남는 것

- 기존 1060곡은 아직 파형이 없다. `music-preprocessing waveform` 명령이 채운다.
- 음원을 갈아 끼우면서 파형만 안 올리는 경로가 생기면 옛 파형이 남는다. 지금은
  `batch` 한 경로로 묶여 있다.
