# 0022. 재생 큐는 Redis 에 사용자당 문서 하나로 둔다

**상태** 제안

## 맥락

재생 큐를 독(dock) 형태 UI 로 바꾸면서, 지금까지 브라우저에만 있던 큐를
**사용자별 서버 상태**로 올린다.

현재 큐는 프론트 메모리에만 있다 — [`use-mupid.ts:72`](../../../frontend/hooks/use-mupid.ts) 의
`queueIds` useState. 새로고침하면 사라지고 서버는 큐의 존재 자체를 모른다.
상한 `QUEUE_LIMIT = 100` 은 이미 있지만 정책이 **가득 차면 거절**이라
(`use-mupid.ts:1134`) 이번 요구사항과 반대다.

요구사항은 다음과 같다.

1. 100곡 상한. 초과해서 담으면 **가장 오래된 곡이 빠진다** (거절이 아니다).
2. 순서 조정 · 중간 삽입 · 삭제가 된다.
3. 새로고침해도, 로그아웃 후 다시 로그인해도 유지된다.
4. 플레이리스트를 전체 재생하면 큐가 그 수록곡으로 **통째로 교체**되고 첫 곡이 재생된다.

팀 논의에서 "큐 데이터를 RDB 말고 Kafka 로 하자" 는 제안이 나왔다. 이 ADR 은
그 제안을 포함해 저장소를 고른 기록이다.

## 후보

| | 방법 | 판단 |
|---|---|---|
| A | **Kafka 토픽**에 큐를 담는다 | **불가.** 아래 상술 |
| B | **MySQL 행 모델** `play_queue_item(user_id, track_id, position)` | 가능하지만 이득이 없다. 순서 조정 한 번에 100행의 `position` 을 갱신해야 하고, 플레이리스트 전체 재생은 전량 삭제 + 대량 삽입을 한 트랜잭션에 묶어야 한다. 그렇게 정규화해 놓고도 **큐 내부를 질의할 일이 없다** — 언제나 한 사용자의 큐를 통째로 읽고 통째로 쓴다 |
| C | **Redis 에 사용자당 JSON 문서 하나** | 채택 |

### A 를 버린 이유

Kafka 는 이 프로젝트에서 이미 청취 이벤트 경로로 쓰고 있어([0005](0005-kafka-clickhouse-for-listen-events.md))
자연스러운 제안처럼 보이지만, 큐의 **저장소**로는 성립하지 않는다.

- **"키별 최근 N건 유지" 라는 보존 정책이 Kafka 에 없다.** 있는 것은
  `retention.ms` · `retention.bytes`(파티션 단위 시간·용량)와 log compaction
  (키별 **최신 1건**) 뿐이다. 사용자별 100곡 상한은 결국 애플리케이션이 직접
  세야 하고, 그러려면 현재 상태를 읽을 다른 저장소가 필요해진다.
- **순서 조정·중간 삭제가 표현되지 않는다.** append-only 로그는 추가와 재생(replay)
  만 준다. 순서 하나 바꾸자고 큐 전체를 다시 발행하는 구조가 된다.
- **점 조회가 없다.** "사용자 X 의 현재 큐" 를 얻으려면 컨슈머가 상태를
  materialize 해야 하는데, 그 상태는 어차피 Redis 나 MySQL 에 들어간다.
  Kafka 는 저장소가 아니라 중간에 낀 홉 하나가 된다.
- **즉시 읽기가 깨진다.** 곡을 담으면 독에 바로 떠야 하는데 발행은 비동기다.
  [`EventServiceImpl.publish()`](../../src/main/java/com/osundosun/mupid/api/event/service/EventServiceImpl.java)
  는 의도적으로 브로커 응답을 기다리지도 않는다.

**Kafka 가 맞는 자리는 따로 있다** — 아래 "따라온 것" 참고.

### B 대신 C 인 이유

성능이 아니다. 디바운스가 붙으면 MySQL 쓰기 부하도 문제되지 않는다.
**이 Redis 가 이미 영속이기 때문**이다.

- [`infra/deploy/compose.yml`](../../../infra/deploy/compose.yml) — `redis-server --appendonly yes` + `redis-data` 볼륨
- [`infra_k8s/base/redis.yaml`](../../../infra_k8s/base/redis.yaml) — 동일하게 AOF + 5Gi PVC

AOF 가 켜져 있고 디스크 볼륨이 붙어 있으므로 재시작해도 남는다. 요구사항 3
("로그아웃 후에도 유지")은 *RDB 여야 한다*는 뜻이 아니라 *서버에 영속으로
저장한다*는 뜻이고, 이 Redis 가 그것을 만족한다. 새 테이블도 DDL 도 필요 없다
([0011](0011-jpa-manages-schema.md) 에 따라 스키마 변경은 수작업이다).

## 결정

**사용자당 JSON 문서 하나를 Redis 에 둔다.**

```
키   {MUPID_REDIS_KEY_PREFIX}queue:{userId}
값   { "revision": 12, "currentTrackId": 3391, "trackIds": [41, 12, 887, ...] }
```

`CacheKind` 에 항목을 추가해 기존 [`CacheService`](../../src/main/java/com/osundosun/mupid/api/cache/service/CacheService.java)
위에 얹는다. Redis List 가 아니라 **문자열 한 덩어리**다 — 순서 조정이 요구사항에
있는 순간 리스트를 어차피 다시 써야 하고(`LSET` 으로는 스왑밖에 안 된다),
플레이리스트 교체도 `DEL` + `RPUSH` 전량이다. 문서로 두면 모든 연산이
**읽기 → 서버에서 배열 조작 → 쓰기** 하나로 통일된다.

### 지키는 규칙

1. **새 곡은 재생 중인 곡 바로 아래에 삽입한다.**
   "최근에 담은 것이 위" 를 글자 그대로 맨 위 삽입으로 구현하면, 3번째 곡을
   재생 중일 때 담은 곡이 1번 자리(재생 커서 **뒤**)로 가서 영영 재생되지 않는다.
   재생 중인 곡 바로 아래에 넣으면 "최근 것이 위쪽" 이라는 인상은 유지하면서
   반드시 다음에 재생된다.

2. **퇴출은 꼬리(맨 아래)에서 한다.** 규칙 1 을 따르면 새 곡이 계속 위쪽에
   끼어들므로 **꼬리로 갈수록 오래 담긴 곡**이 된다. 즉 "맨 아래 = 가장 오래된 곡"
   이 자연히 성립한다.

3. **담은 시각을 저장하지 않는다.** 수동으로 순서를 바꾸면 위치와 담은 시각이
   어긋나는데, 이때 **위치를 기준으로 못 박는다.** 사용자는 화면에 보이는
   맨 아래 곡이 빠질 것이라고 읽기 때문이다. 담은 시각 기준으로 빼면 목록
   중간에서 곡이 사라지는 것처럼 보인다.

4. **재생 중인 곡은 퇴출하지 않는다.** 꼬리가 재생 중인 곡이면(사용자가 끌어
   내렸을 때) 그 바로 위 항목을 뺀다.

5. **퇴출은 알린다.** 토스트 — `100곡이 초과되어 가장 오래된 곡이 삭제됩니다.`
   기존의 거절 토스트(`재생 목록은 100곡까지 담을 수 있어요…`)는 없앤다.

6. **플레이리스트 전체 재생은 전량 교체다.** `trackIds` 를 수록곡으로 바꾸고
   `currentTrackId` 를 첫 곡으로 둔다. 큐를 통째로 갈아엎는 연산이라 문서 모델에
   가장 잘 맞는다 — `SET` 한 번이다.

7. **플레이리스트에도 100곡 상한을 건다.** 규칙 6 과 상한이 충돌하지 않으려면
   두 곳의 제약이 같아야 한다. 지금 플레이리스트에는 수록곡 상한이 없어
   ([`PlaylistTrackRepository`](../../src/main/java/com/osundosun/mupid/api/playlist/repository/PlaylistTrackRepository.java))
   150곡짜리를 전체 재생하면 50곡이 조용히 잘린다. `PlaylistErrorCode` 에
   `PLAYLIST_TRACK_LIMIT_EXCEEDED`(409 — 요청은 유효하나 현재 상태 때문에 거절)
   를 추가하고 곡 추가 시점에 막는다.

8. **동시성은 `revision` 으로 잡는다.** 클라이언트가 읽은 리비전을 같이 보내고,
   서버는 Lua 스크립트로 "리비전이 같을 때만 교체" 를 원자적으로 처리한다.
   어긋나면 거절하고 서버 상태를 내려주며, 클라이언트는 그것으로 갈아엎는다.
   큐는 병합할 가치가 없는 데이터라 CRDT 같은 것은 쓰지 않는다.

9. **TTL 90일, 접근할 때마다 갱신한다.** 장기 미접속 사용자의 큐가 메모리를
   영구 점유하는 것을 막는다.

10. **프론트는 지금처럼 메모리에서 즉시 반응하고, 디바운스해서 올린다.**
    드래그 한 번마다 왕복을 걸면 순서 조정이 끊긴다. 1~3초 모아서, 그리고
    일시정지·이탈 시점에 보낸다. 상한과 퇴출은 **프론트와 서버 양쪽에서 같은
    규칙으로** 적용한다 — 프론트는 토스트를 띄우려고, 서버는 클라이언트를
    믿지 않으려고.

### 곡 정보는 읽을 때 채운다

Redis 에는 곡 번호만 넣는다. 독 UI 가 필요로 하는 제목·아티스트·커버는 조회
시점에 MySQL 에서 채운다. 도구가 이미 있다 —
[`MusicSummaryAssembler.byIds()`](../../src/main/java/com/osundosun/mupid/api/music/service/MusicSummaryAssembler.java)
는 **넘긴 순서를 그대로 지키고 삭제된 곡은 빼고** 돌려준다. 큐 조회가 정확히
이 시그니처다.

덤으로 Redis 에 제약조건이 없어서 생기는 문제가 여기서 해결된다. 큐에 남은
삭제된 곡 번호는 조립 단계에서 자연히 걸러진다([0013](0013-soft-delete-policy.md)).
데모 곡(1~8)도 서버에 없으므로 같은 경로로 빠진다.

## 결과

### 얻은 것

- 요구사항 네 가지가 저장소 하나로 덮인다. 새 테이블·DDL·마이그레이션이 없다.
- 플레이리스트 전체 재생이 `SET` 한 번이다.
- 삭제된 곡 정리가 조회 경로에 흡수된다.

### 받아들인 비용

- **Redis 의 역할이 캐시에서 저장소로 넓어진다.** 지금까지 Redis 에 있던 것은
  전부 잃어도 재구성 가능한 데이터였다 — 차단 토큰([0004](0004-jwt-denylist-in-redis.md)),
  이벤트 멱등 키, 리포트 캐시. **큐는 잃으면 복구할 수 없다.** AOF 와 PVC 설정에
  서비스 데이터가 걸리게 된다. 이 둘을 끄거나 볼륨을 날리는 변경은 이제
  데이터 손실이다.
- **큐는 이 Redis 의 첫 무기한 키다.** 기존 키는 전부 TTL 이 붙어 있다.
  `maxmemory-policy` 가 설정돼 있지 않아 가득 차면 키가 밀려나는 게 아니라
  **컨테이너가 죽는다**(k8s 메모리 한도 512Mi). 사용자당 1KB 남짓이라 수십만
  명까지 여유롭지만, 규칙 9 의 TTL 이 사실상 유일한 방어선이다.
- **큐 내부를 질의할 수 없다.** "이 곡을 큐에 담아 둔 사용자 수" 같은 것은
  못 뽑는다. 필요해지면 아래의 이벤트 경로로 간다.
- **상태가 프론트와 서버 두 곳에 산다.** 규칙 8·10 으로 관리하지만, 이중
  상태 자체는 남는다.
- **기존 100곡 초과 플레이리스트가 있다면 그대로 남는다.** 규칙 7 은 검증만
  추가하므로 읽기는 막지 않는다. 그런 플레이리스트를 전체 재생하면 앞 100곡만
  담긴다.

## 따라온 것

**Kafka 를 쓰자는 제안 자체가 무의미하지는 않다.** 큐 변경을 *이벤트*로 흘리는
것은 정당하다. `QUEUE_ADD` · `QUEUE_REMOVE` · `QUEUE_EVICT` 를 기존
`mupid.listen.events` 에 얹으면 "담고 안 들은 곡", "밀려나서 못 들은 곡" 같은
분석이 ClickHouse 에서 나오고, 추천 품질 지표로 쓸모가 있다.

즉 **상태는 Redis, 이벤트는 Kafka** 로 가른다. [0018](0018-history-from-event-stream.md)
이 "이벤트는 Kafka, 화면이 읽는 사본은 MySQL" 로 갈라 놓은 것과 같은 구조다.
이벤트 발행은 이번 범위가 아니라 후속 과제로 둔다.

## 다시 볼 것

규칙 1~4 는 "재생 순서" 와 "담은 순서" 라는 서로 다른 두 개념을 목록 하나로
표현하려는 타협이다. 수동 순서 조정이 끼면 둘은 반드시 어긋나고, 그때 어느
쪽을 보여줄지는 규칙 3 에서 "위치" 로 정했을 뿐 자명한 답이 아니다. 사용자가
큐를 "다음에 들을 것" 으로 읽는지 "담아 둔 것" 으로 읽는지 확인되면 다시 볼 값이다.
