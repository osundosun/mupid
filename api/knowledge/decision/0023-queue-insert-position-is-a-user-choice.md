# 0023. 담을 자리는 사용자가 고르고, 큐에 같은 곡은 한 번만 둔다

**상태** 채택 · [0022](0022-play-queue-in-redis.md) 의 규칙 1~5 를 대체

## 맥락

[0022](0022-play-queue-in-redis.md) 는 담은 곡을 **재생 중인 곡 바로 아래**에 넣기로
못 박았다. 그렇게 정한 까닭은 "최근 담은 것이 위" 를 글자 그대로 맨 위 삽입으로
구현하면 새 곡이 재생 커서 뒤로 가서 영영 재생되지 않기 때문이었다.

그 사이 두 가지가 겹쳤다.

1. **자리(uid) 모델이 들어왔다.** 큐의 단위가 곡 번호가 아니라 자리가 되면서
   (`frontend/lib/queue.ts`) 같은 곡을 여러 번 담을 수 있는 구조가 됐다.
2. **회의에서 자리를 사용자가 고르기로 했다.** 한 자리에 못 박는 것이 아니라
   맨 위·맨 아래·재생 중인 곡 다음 중에서 고르게 한다.

`afterCurrent` 하나만 두면 "지금 듣는 흐름을 깨지 말고 뒤에 쌓아 줘" 라는 쓰임을
받을 수 없다. 반대로 맨 아래 고정이면 0022 가 막으려던 문제 — 담은 곡이 한참
뒤에나 들리는 것 — 가 돌아온다. 둘 다 정당한 요구라 고르게 한다.

## 결정

### 1. 담을 자리는 세 갈래이고 사용자가 고른다

| 값 | 자리 |
|---|---|
| `bottom` | 맨 아래 **(기본값)** |
| `top` | 맨 위 |
| `afterCurrent` | 지금 재생 중인 곡 바로 다음 |

기본값이 `bottom` 인 것은 재생 중인 흐름을 건드리지 않는 쪽이 놀라움이 가장
적어서다. 고른 값은 **계정이 아니라 기기에 남긴다**(`localStorage`). 화면에서는 독 머리글의
버튼으로 열고 고른다 — 라디오를 목록 위에 펼쳐 두었더니 정작 보러 온 목록이 밀려났다. 큐 자체는
계정에 붙지만 이것은 "이 기기에서 담을 때의 버릇" 에 가깝다.

### 2. `afterCurrent` 인데 듣는 곡이 없으면 맨 아래로 내리고 **알린다**

재생 중인 자리가 없으면 기준점이 없다. 그때는 맨 아래에 담되 토스트로
`재생 중인 곡이 없어 맨 아래에 담았어요.` 라고 말한다. **조용히 다른 자리에 넣으면
설정이 안 먹은 것으로 읽힌다.** 고르는 것 자체를 막지는 않는다 — 곧 곡을 틀 사람에게는
미리 골라 두는 것이 자연스럽다.

듣던 자리가 큐에서 빠진 뒤(재생 중인 곡을 목록에서 뺀 경우)도 같은 길로 간다.

### 3. 큐에 같은 곡을 두 번 담지 않는다 — 다시 담으면 **옮긴다**

자리 모델은 중복을 담을 수 있지만 **담지 않기로 한다.** 이미 담긴 곡을 또 담거나
재생하면 거절하지 않고 그 자리를 걷어 **새 자리로 옮긴다.** 거절하면 방금 한 행동이
아무 일도 하지 않은 것처럼 보이고, 그대로 두면 담은 곡이 목록 어딘가에 묻혀 있어
역시 담긴 것처럼 보이지 않는다.

옮긴 자리는 **새 자리 번호를 받는다.** 번호를 물려주면 화면이 같은 줄로 보고
자리를 옮기지 않는다.

재생은 **어디서 눌렀는지**로 갈린다.

| 누른 곳 | 자리 |
|---|---|
| 재생 목록 **밖** (검색·추천·상세) | **맨 위로 올린다** |
| 재생 목록 **안** (독의 줄) | **그 자리 그대로** |

밖에서 튼 곡이 목록 한참 아래에 그대로 있으면 지금 무엇을 듣는지 찾기 어렵다.
반대로 목록에서 고른 줄이 누르자마자 맨 위로 튀어 오르면 방금 어디를 눌렀는지
놓친다. 줄에서 부르는 쪽은 자리 번호를 함께 넘겨 그 자리를 그대로 튼다.

일시정지·재개는 큐를 건드리지 않고, **자동으로 다음 곡이 넘어가는 길도 마찬가지다** —
넘어갈 때마다 맨 위로 끌어올리면 애써 잡은 순서가 매 곡마다 뒤집힌다.

자리 모델은 그대로 쓴다. 중복이 없어도 자리 번호는 값어치가 있다 — 순서를 바꿀 때
React 가 줄을 다시 만들지 않아 끌던 줄이 손에서 놓이지 않고, 건너뛴 곡을 감춘
자리를 되짚을 수 있다(`reorderQueue`).

### 4. 퇴출은 **새 곡이 들어온 반대쪽 끝**에서 한다

담을 자리가 셋이 되면서 "맨 아래가 가장 오래된 곡" 이 늘 참이 아니게 됐다.
쌓이는 방향의 반대쪽이 가장 오래 머문 자리다.

| 담는 자리 | 미는 쪽 |
|---|---|
| `bottom` | 위쪽 |
| `top` | 아래쪽 |
| `afterCurrent` | 아래쪽 (재생 커서에서 가장 먼 곳) |

지금 울리는 자리와 **방금 놓은 자리**는 건너뛴다. 방금 놓은 것을 도로 빼면 담기
버튼이 헛도는 것처럼 보인다 — 0022 때 실제로 그랬다.

이미 담긴 곡을 옮기는 경우에는 곡 수가 늘지 않으므로 아무도 밀려나지 않는다.

### 5. 자리는 **화면이 정한다.** 서버는 결과만 받는다

0022 는 "자리와 퇴출은 서버가 판정한다" 였다. 자리가 사용자 설정이 된 이상 그럴 수
없다 — 서버가 다시 계산하면 사용자가 고른 자리를 덮는다.

그래서 큐 영속은 **전체 교체 한 경로**(`PUT /api/v1/user/queue`)로 모은다. 담기·빼기
전용 요청(`POST`·`DELETE /track`)은 이 화면에서 쓰지 않는다. 두 경로가 섞이면 판본이
엇갈려 한쪽이 409 로 튕긴다.

서버가 여전히 지키는 것은 **중복 거절**(`QUEUE_DUPLICATED_TRACK`)과 상한이다.
규칙 3 과 같은 방향이라 그대로 둔다.

## 결과

### 얻은 것

- 담는 자리를 두고 벌어지던 요구 충돌이 설정 하나로 정리된다.
- 중복이 없어 "이 곡을 뺀다 / 이 곡이 담겨 있다" 가 곡 번호만으로 명확하다.
- 배치 규칙이 순수 함수(`lib/queue.ts` 의 `placeInQueue`)라 화면 없이 검증된다
  (`frontend/tests/queue-placement.test.mjs`, 14건).

### 받아들인 비용

- **고른 자리는 기기에만 남는다.** 다른 기기에서는 기본값(`bottom`)으로 시작한다.
  계정에 담으려면 사용자 설정 API 가 필요한데, 이 값 하나를 위해 만들지 않았다.
- **`POST`·`DELETE /track` 이 이 화면에서 쓰이지 않는다.** API 와 테스트는 남아
  있지만 호출부가 없다. 다른 클라이언트가 자리를 서버에 맡기고 싶을 때 쓰는 길로 둔다.
- **퇴출 기준이 담는 자리에 따라 달라진다.** 사용자가 설정을 바꾸면 "가장 오래된 곡"
  이 가리키는 쪽도 바뀐다. 담은 시각을 따로 저장하면 설정과 무관해지지만, 그 값을
  서버 문서에 넣어야 해서 이번에는 위치로 갈음했다.

## 다시 볼 것

규칙 4 는 "쌓이는 방향의 반대쪽이 가장 오래됐다" 는 근사다. 사용자가 순서를 손으로
바꾸거나 설정을 오가면 어긋난다. 큐가 실제로 100곡까지 차는 일이 흔해지면 담은 시각을
자리에 붙이고(서버 문서에 한 줄 더) 그걸로 퇴출을 정하는 쪽이 정확하다.
