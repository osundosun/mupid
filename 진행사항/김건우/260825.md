## 아이디어별 피드백

### 1. 밥상레이더 (예산 맞춤 식단 추천)

- 가격 예측 모델 구축 여부가 핵심 쟁점
  - 뉴스 데이터는 벡터 검색으로 처리 가능해 보임
  - 날씨 요인은 어떤 근거로 어떤 농산물에 영향을 주는지 검증 필요 — 가뭄·장마 등 원인이 다양해 단일 근거로 확정하기 어려움
  - 농작물별 영향 요인의 원인·근거를 명확히 정리할 필요
- 제철 파악 기반 예측은 상대적으로 타당
- 동일 품목이라도 지역별 원인(태풍 vs 작황)이 다를 수 있어 원인을 하나로 고정하기 어려움 → 모델/알고리즘 보강 필요
- 날씨만으로는 부족 — 전염병, 인건비 등 미보도 요인까지 포괄 가능한지 확인 필요
- 서비스 주체와 후속 행동(가격 예측 이후 무엇을 할지) 명확화 필요
- 사후약방문식 서비스가 되지 않도록 설계 방향 고민 필요

### 2. 우리농지 작물추천

- 수익성 높은 작물로 쏠림 현상 우려 (예: 샤인머스캣류 쏠림)
  - 보완안: 후보군 확대, 커뮤니티 기반 데이터 수집, 흙토람 데이터 활용
- 잘 자라는 것과 잘 팔리는 것은 별개 — 지역 특산물·브랜드 파워 반영 필요
- 농민이 품종을 자주 바꾸기 어려움 (밭 작물은 상대적으로 유연)
- 지역 구분 기준, 날씨 구분 기준(연 단위/평균/최고기온/강수량) 미정
- 빅데이터 활용 범위에 의문 — 데이터 규모가 제한적일 가능성 (추정 30만 건 내외)
- 올해 잘 팔린 품종이 내년에도 유효할지 불확실

### 3. 에피제로 (전염병 확산 예측)

- 이미 정부 운영 서비스 존재 — 차별화 필요
- 확산 요인으로 차량 이동 GPS 데이터 활용 검토
  - 시뮬레이션 데이터인지 실데이터인지 구분 필요
  - 전체 차량 방문 이력 확보는 비현실적 — 이동 순서 기반 유추 방식 고려
  - 예: A→B, B→C 이동량 기반으로 길목(A-B 구간) 소독 등 예방 조치 설계
- 실시간 확진 데이터 활용은 빅데이터 관점에서 의미 있음
- 핵심은 초동조치 설계 — 차량별 가중치 기반 확률 분석 필요
- 데모/시연 방식이 관건 (기획 자체는 양호)
- 심각 단계 도달 후 대응은 이미 늦을 가능성 — 조기 대응 설계 필요

### 4. 육류 시그널 (한우 등급 예측)

- 개별 농가 데이터 입력 방식은 현실적으로 부담 (대량 사육 구조와 불일치 가능)
- 어린 개체 상태만으로 발달 정도 예측 가능 여부 확인 필요
- AI 모델 대비 현업 사육사의 경험치가 더 정확할 가능성 — 정확도 확보가 관건
- 생후 개월수·체중 기준 등급 예측 방식 검토
- 동일 농가·동일 사료에도 등급 편차가 클 수 있음 → 개체별보다 집단 단위 예측 방식 검토
- 예측 단위는 단기(시간 단위)보다 축산물 특성상 며칠 이상 단위가 적절

## 인프라 학습

음악 추천 서비스는 오디오 디코딩·특징 추출·임베딩 생성처럼 CPU/GPU 부하가 큰 배치 작업과, 실시간 서빙(추천 API)이 함께 필요함. 이 둘을 하나의 서버에 몰아넣지 않고 역할별로 분리하는 구조를 학습.

```
EC2 #1 (서빙)
────────────────
Backend
Recommendation
PostgreSQL
Redis
Monitoring

EC2 #2 (오디오 전처리)
────────────────
Audio CPU Worker
Decode
Essentia Feature
Job Producer

GPU Server (임베딩)
────────────────
GPU Worker
Audio Embedding
Batch Inference

S3 / Object Storage
────────────────
Jamendo Audio
Intermediate Data
Analysis Result
```

- **EC2 #1 — 서빙 서버**: Backend API, 추천 로직(Recommendation), 사용자·트랙 메타데이터를 담는 PostgreSQL, 세션·캐시·랭킹 캐싱용 Redis, Monitoring(지표 수집)을 배치. 사용자 요청을 직접 받는 계층이라 CPU 집약 배치 작업과 분리해야 응답 지연이 안 생김.
- **EC2 #2 — 오디오 CPU 워커**: Jamendo 원본 오디오 Decode, Essentia 기반 Feature 추출(BPM/Energy/Rhythm/Timbre 등)을 수행하고 GPU 워커로 넘길 Job을 Producer로 적재. CPU 바운드 작업이라 서빙 서버와 물리적으로 분리.
- **GPU Server — 임베딩 워커**: Audio Embedding 생성과 Batch Inference 전담. GPU 자원은 상시 필요하지 않고 배치 처리 시점에만 사용하므로 온디맨드/오토스케일 대상으로 고려.
- **S3 / Object Storage**: Jamendo Audio 원본, 전처리 중간 산출물(Intermediate Data), 분석 결과(Analysis Result)를 저장. EC2 #2 → GPU Server → EC2 #1로 이어지는 파이프라인에서 각 단계 산출물을 S3로 주고받는 구조.

### 파이프라인 흐름

```
S3 (Jamendo Audio)
   ↓ Decode
EC2 #2 (CPU Worker)
   ↓ Feature / Job Producer
GPU Server (Embedding, Batch Inference)
   ↓ Embedding 저장
S3 (Intermediate / Analysis Result)
   ↓ 조회
EC2 #1 (Backend, Recommendation, PostgreSQL, Redis)
   ↓ 응답
사용자
```

- CPU 워커와 GPU 워커를 Job Producer/Consumer 구조로 분리하면, 오디오 수천 곡 단위 배치 처리량이 늘어나도 서빙 서버 성능에 영향을 주지 않음.
- 사용자 행동 이벤트가 쌓여 Listening DNA·추천 Profile을 재계산할 때도 동일하게 EC2 #2/GPU Server 쪽 배치 파이프라인을 재사용 가능.
- Redis는 실시간 랭킹·세션 캐시, PostgreSQL은 트랙/사용자/이벤트 원본 데이터 저장으로 역할 분담.
