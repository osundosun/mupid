# 260826 — 비동기 API와 요청 상태

## 프로젝트 아이디어 기획

### 미래 상태와 성공 가능성을 계산하는 서비스

- **고속도로 정시 도착:** 수년간의 5분 단위 교통 데이터를 분석해 평균 소요시간이 아닌 목표 시각 이전 도착 확률과 안전한 출발시간을 제안
- **전기차 충전 성공률:** 충전기 상태·충전 이력·시간대·날씨를 결합해 사용자가 도착할 시점의 충전 가능성과 예상 대기시간을 계산
- **주차·환승 성공률:** 현재 잔여 주차면이나 교통 도착정보를 보여주는 데서 그치지 않고, 도착 예정 시점의 성공 가능성을 제공

### 안전과 금전 손실을 줄이는 서비스

- **폭우 안전 이동·차량 침수 알림:** 기상 레이더와 과거 침수지역을 시공간으로 연결해 위험 경로를 피하거나 차량 이동이 필요한 시점을 안내
- **직구제품 안전 레이더:** 국내·해외 리콜, KC 인증, 위해정보에서 표현이 다른 제품명을 매칭해 구매 전 확인이 필요한 위험 신호 제공
- **전세 계약 손실 시뮬레이터:** 매매·전월세 실거래와 건축물 정보를 분석하고 가격 하락 시 보증금 회수 여력이 어떻게 달라지는지 비교
- **창업 생존위험 진단:** 전국 음식점 인허가·폐업 이력과 상권 조건을 공간 조인해 비슷한 입지와 업종의 생존기간을 분석
- **나라장터 Bid/No-Bid:** 수년간의 입찰공고·투찰·낙찰 결과를 이용해 중소기업이 어느 공고에 준비 시간을 투입할지 우선순위 제공

### 서로 다른 데이터의 연결에서 의미를 만드는 방향

- 교통사고×기상·도로환경으로 현재 조건에서 위험한 도로 구간 탐색
- 지하철 혼잡×공연·경기·날씨로 평소와 다른 혼잡 원인과 회피 시간 제안
- 도시민원×시설·상권·인구로 특정 민원이 반복되는 조건 분석
- 폐업 이력×유동인구·임대료·경쟁업체로 업종별 상권 위험 신호 탐색

### 후보 평가 결과

- 데이터가 많다는 이유만으로 선정하지 않고 `의미 있는 데이터인가`, `확보 가능한가`, `분산 처리가 실제로 필요한가`, `사용자 행동을 바꾸는가`, `기간 안에 구현 가능한가`를 공통 기준으로 비교했다.
- SSAFY 빅데이터·분산 수상작을 조사해 단순 조회·대시보드보다 대규모 조인·윈도우·공간 또는 시계열 분석 결과가 핵심 기능이 되는 주제가 적합하다고 정리했다.
- 후보를 바로 확정하지 않고 작은 데이터 POC로 건수·용량·컬럼·조인 가능성과 Spark 처리 효과를 검증하기로 했다.

## 학습 목표

- Mock 요청을 `Promise` 기반 비동기 흐름으로 변경한다.
- 요청 상태에 따라 다른 화면을 표시한다.

## 진행 내용

- 동기 Mock 호출을 비동기 `requestQuery` 함수로 변경
- `idle`, `loading`, `success`, `error` 상태 연결
- `useQueryRequest` 커스텀 훅으로 요청 로직 분리
- 로딩 안내와 결과 화면 상태 전환 구현
- 오류 발생 시 기본 안내 문구 표시

## 요청 상태 흐름

```text
idle → loading → success
          └──→ error
```

## 적용한 React·TypeScript 개념

- `Promise<ApiResponse<QueryResult>>` 반환 타입
- `RequestStatus` union type
- `async/await`와 `try/catch`
- 커스텀 훅을 이용한 상태 로직 분리

## 문제 해결

API 호출 상태를 여러 컴포넌트에서 직접 관리하면 코드가 흩어질 수 있어 `useQueryRequest` 훅으로 요청과 상태 변경을 한곳에 모았다.

## 산출물

- Promise 기반 Mock API
- `useQueryRequest` 요청 상태 훅
- 상태 안내와 로딩·성공·오류 화면
