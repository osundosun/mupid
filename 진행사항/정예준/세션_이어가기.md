## 3. 이 저장소에서 밟은 함정

### 여러 클론이 같은 저장소를 공유한다 — 남의 작업을 밟는다

워크트리가 6개다(`big_data_pjt` 는 `develop`, `wt_dbstudio` 는 docs 브랜치 …).
**다른 세션이 브랜치와 cwd 를 바꿔놓는다.** 실제로 이번에 겪은 것:

- `api/knowledge/domain/erd.sql` 이 **내가 아무것도 안 했는데 바뀌어 있었다**
  (mtime 1분 전). 사용자가 ERD 도구에서 재산출해 넣은 것이었다 → **추적하지 않고
  지우면 남의 작업이 사라진다.** 바뀐 파일을 보면 먼저 백업하고 물어본다
- 커밋 전에 `git branch --show-current` 를 확인한다
- cwd 가 흔들리면 `write_file`·`patch` 의 상대경로가 그 cwd 기준으로 풀린다 —
  **절대경로(`C:/…`)를 쓴다**

### `schema-check.py` 가 `AUTO_INCREMENT`·인덱스를 못 보던 문제 (고침)

`information_schema.columns` 의 `table_name, column_name, column_type` 만 읽었다.
그런데 **`AUTO_INCREMENT` 는 `extra` 에 있고 인덱스는 `statistics` 에 있다.**
그래서 `music_analysis_instruments` 의 `AUTO_INCREMENT` 와
`music_section_analysis.external_id` 의 UNIQUE 가 **정반대여도 "차이 없음"** 이
나왔다. 둘 다 2026-09-17 에 고쳤다(`extra` + `statistics`, 엔티티 `@GeneratedValue`
대조까지).

**인덱스는 이름을 비교하지 않는다.** ERD 도구가 이름을 바꾼다(`uk_` → `ux_`).
`(테이블, 컬럼집합, 유니크)` 로만 본다. 이름까지 보면 재산출할 때마다 가짜 차이가
나서 DDL 을 다시 치게 된다.

**고치면서 내가 만든 버그 둘 — 다시 밟기 쉬우니 적어 둔다.**

- `CREATE TABLE` 블록을 `\n)` 로 끊으면 **`COMMENT='…'` 로 닫히는 표를 놓친다.**
  본문이 다음 표까지 이어져 없는 컬럼이 있는 것처럼 보인다. **괄호 깊이로 끊는다**
- 인덱스를 **컬럼으로만 묶으면 복합 인덱스가 쪼개진다.** 컬럼마다 한 줄로 오므로
  `(code_type)`·`(code_name)` 이 따로 잡혀 `(code_type, code_name)` 을 영영 못
  찾는다 → 운영에 있는 유니크 7개를 "없다" 고 잘못 보고했다. **묶는 데는 이름을
  쓰고 판정에는 쓰지 않는다**

### ERD 도구는 `--` 주석을 보존하지 않는다

재산출하면 **`erd.sql` 안의 사람 주석이 전부 사라진다.** 커밋 `b6d5c7e` 가 붙였던
근거(왜 `AUTO_INCREMENT` 가 틀린지, `external_id` 가 50→64 인지)도 그렇게 없어졌다.
**지식은 `erd.sql` 이 아니라 `erd.md` 에 적는다.** `erd.sql` 에 손으로 주석을
넣으면 다음 재산출에 사라진다.

### 임시 테이블은 반드시 지운다 — 스크립트가 중간에 죽으면 남는다

재현용 임시 표를 만들어 검증한 뒤 "전부 DROP 했다" 고 보고했는데 **사실이 아니었다.**
재현 스크립트가 마지막 `INSERT` 에서 `ERROR 1452` 로 중단돼 맨 끝 `DROP` 에
도달하지 못했다. `schema-check` 가 "erd.sql 에 없는 테이블 3개" 로 잡아 줘서 알았다.

**검증용 스크립트는 실패해도 정리되게 쓴다.** 그리고 남았는지 실제로 확인한다.

### CRLF

저장소는 LF 로 저장하는데 **작업 트리는 CRLF** 다(`core.autocrlf=true`). Write 도구로
만든 파일은 LF 라 그냥 쓰면 diff 가 통째로 바뀐 것처럼 보인다.

### `git checkout develop` 이 안 된다

```
fatal: 'develop' is already used by worktree at 'C:/Workspace/big_data_pjt'
```

여기는 워크트리다. `git checkout -B <새이름> origin/develop` 을 쓴다.
`git stash` 스택도 다른 워크트리와 공유되므로 **bare `git stash` / `pop` 을 쓰지 않는다
— `git stash push -- <경로>` 로 범위를 좁힌다**(이번에 그렇게 했다).

### `glab`

- `--state` 플래그가 없다 (`gh` 와 다르다). `glab api "projects/<enc>/merge_requests?state=merged"` 를 쓴다
- `glab api` 에 `--jq` 가 없다. 파이프로 파이썬에 넘기고 **stdin 을 직접 utf-8 로 디코드**한다
  (윈도우 기본 코드페이지로 읽히면 한글이 깨진다)
- **원본 브랜치 보전은 만든 뒤에 따로 껴야 한다.** 프로젝트 기본값이 삭제다
  ```bash
  glab api --method PUT 'projects/<enc>/merge_requests/<iid>' -f remove_source_branch=false
  ```
  판단은 `force_remove_source_branch` 필드로 한다 (`should_remove_source_branch` 는 null 이 정상)

### CI — 라벨이 파이프라인을 고른다

MR 에 **영역 라벨(Frontend·Backend·AI·Data)이 없으면 `require-area-label` 이 막는다.**
라벨이 job 을 고르므로, `music_preprocessing` + `ai_server/tests` 를 같이 건드리면
**Data 와 AI 둘 다** 붙여야 양쪽이 돈다.

그리고 **`backend-verify` 는 `build -x test` 다.** Java 통합 테스트는 CI 에서 안 돈다 —
초록불이 곧 테스트 통과가 아니다. 로컬 MySQL 로 직접 돌려야 한다.

### 한글 출력이 죽는다

윈도우 기본 코드페이지(cp949)로 `—` 같은 문자를 찍으면 `UnicodeEncodeError` 로
스크립트가 중간에 죽는다. **파일을 고치는 스크립트가 출력에서 죽으면 반쯤 고친 상태로
남는다** — 실제로 한 번 그랬다.

```bash
PYTHONIOENCODING=utf-8 python ...
```

고치는 것과 찍는 것을 분리하고, `try/finally` 로 원복을 보장한다.

### 명령이 길면 하네스가 막는다

한 줄이 너무 길거나 인용이 복잡하면 `BLOCKED (hardline)` 로 실행이 거부된다.
**스크립트 파일로 뺀다**(`write_file` → `bash <파일>`). 이번에 `schema-dump-local.sh`
가 그렇게 태어났다.

### `bash $PWD` / `mktemp` 경로를 네이티브 도구가 못 읽는다

MSYS 경로(`/c/Users/…`, `/tmp/…`)를 네이티브 `kubectl`·`python` 이 못 읽는다.
`cygpath -m` 으로 바꾸거나 처음부터 `C:/…` 로 쓴다. `ssh` 는 argv 를 한 문자열로
합쳐 인용을 잃으므로 `printf %q` 로 조립한다.

### 백틱이 든 텍스트를 `python -c` 로 쓰지 않는다

bash 가 백틱을 명령 치환으로 먹어 **내용이 조용히 사라진다.** `write_file`·`patch`
를 쓴다.

## 4. 이 도메인에서 조심할 것

- **"성공으로 끝나는데 동작만 안 되는"** 실패가 이 프로젝트의 주된 고장 유형이다.
  배포 job 이 성공인데 클러스터가 깨져 있고, 온보딩이 200 인데 개인화가 0 이고,
  악기가 엉뚱한 구간에 붙는데 외래키 검사는 통과한다. **조용히 비는 것을 의심한다**

### `AUTO_INCREMENT` 는 PK 자리에만 — 오류 없이 어긋나는 자리

**FK 자리에 `AUTO_INCREMENT` 가 붙으면 `0` 이 새 번호로 발급된다.** 로컬 재현
(운영과 같은 모양의 임시 표):

```sql
INSERT INTO links (section_id, code_id) VALUES (1, 100);   -- 1번 구간에 기타
INSERT INTO links (section_id, code_id) VALUES (0, 200);   -- 값이 0으로 들어온 경우

section_id  code_id
    1         100
    2         200     ← 0을 넣었는데 2가 됐다. 외래키 검사도 통과했다
```

**세 가지가 겹쳐 조용히 어긋난다.** ① 발급된 번호가 마침 존재하는 구간 번호라
외래키 검사를 통과한다 ② 오류가 안 난다(응답 200, 화면 정상) ③ 떼면 같은 INSERT 가
`ERROR 1452` 로 시끄럽게 실패한다 — 그게 맞는 동작이다.

**지금 당장 터지지는 않는다.** JPA 경로는 `@MapsId` 가 실제 PK 를 채워 보내므로
`0` 이 갈 일이 없다. 위험한 것은 **손으로 쓴 SQL · 벌크 로더 · id 가 채워지지 않은
INSERT** 다. 자세한 근거는 `erd.md` 104행.

`music_section_analysis.music_section_analysis_id` 는 **이름이 같아도 다른 표**라
`AUTO_INCREMENT` 가 맞다. 표를 확인한다.

### 아직 DB 에 적용하지 않은 DDL — 2026-09-17 실측

`erd.sql` 이 **최종 모양**을 적고 DB 가 뒤처져 있다. `ddl-auto: none` 이라 앱이 안
바꾼다. **사람이 직접 실행한다.** 운영 3건 / 개발 1건(개발은 손으로 고쳐 둔 게 있다).

| | 대상 | 지금 DB | erd.sql | 운영 | 개발 |
|---|---|---|---|---|---|
| ① | `music_analysis_instruments.music_section_analysis_id` | `int auto_increment` | `int` | 미적용 | 미적용 |
| ② | `music_section_analysis.external_id` UNIQUE | 없음 | 있음 | 미적용 | **적용됨** |
| ③ | `codes.display_name` | 컬럼 없음 | `VARCHAR(200)` | 미적용 | **적용됨** |

```sql
-- ② 를 먼저. 행이 들어온 뒤엔 중복 때문에 실패할 수 있다 (세 테이블 모두 0행인 지금이 제일 싸다)
ALTER TABLE music_section_analysis
  ADD UNIQUE KEY uk_music_section_analysis_external_id (external_id);

-- ① FK 를 먼저 떼야 MODIFY 가 통과한다. 붙은 채면 ERROR 1832 로 거부된다
ALTER TABLE music_analysis_instruments
  DROP FOREIGN KEY fk_music_analysis_instruments_music_section_analysis_id;
ALTER TABLE music_analysis_instruments
  MODIFY music_section_analysis_id INT NOT NULL;
ALTER TABLE music_analysis_instruments
  ADD CONSTRAINT fk_music_analysis_instruments_music_section_analysis_id
  FOREIGN KEY (music_section_analysis_id)
  REFERENCES music_section_analysis (music_section_analysis_id);

-- ③ 앱보다 먼저. 없으면 스프링 컨텍스트가 못 떠서 모든 @SpringBootTest 가 죽는다
ALTER TABLE codes ADD COLUMN display_name VARCHAR(200) NOT NULL AFTER code_name;
UPDATE codes SET display_name = code_name WHERE display_name = '';
```

인덱스 이름이 곳에 따라 다르다 — `erd.sql` 은 `ux_…`, 위 DDL·개발 DB 는 `uk_…`.
**게이트가 이름을 보지 않으므로 문제 없다.**

### `codes` 는 이름을 두 벌 갖는다 — 방향이 종류마다 반대다

| 컬럼 | 무엇 | 예 |
|---|---|---|
| `code_name` | **AI 색인과 맞추는 값.** 스프링이 AI 서버로 넘긴다 | 장르 `poprock`, 무드 `애상적인` |
| `display_name` | **화면에 그릴 값** | 장르 `팝 록`, 무드 `melancholic` |

장르 45종은 `code_name` 이 색인 원문이고 `display_name` 이 나중에 한국어가 된다.
**taxonomy 무드 9종은 반대다** — `code_name` 이 화면용 한국어(`애상적인`),
`display_name` 이 색인 원문(`melancholic`). 무드 9종이 기존 8종(`잔잔한`)과 같은
방향이기 때문이다.

기준은 하나다: **`AiRecommendToolImpl` 이 `CodeOption::name`(= `code_name`)을 보낸다.**
여기에 한국어가 실수로 들어가면 색인에 없는 말이 가서 **씨앗이 0 이 되는데 오류는
나지 않고 개인화만 사라진다.**

### 무드 어휘가 두 벌이다 — 지우면 안 되는 값이 있다

`/facets` 의 `mood` 선택지 27종과 태그 어휘 38종이 다르다. `slow`·`party`·`sad`·
`dark` 는 **선택지에는 없지만 태그 어휘에는 살아 있고**, `MOOD_BY_TAG` 역방향 표에서
`감성적인`·`강렬한` 라벨을 지탱하는 유일한 근거다. **"죽은 값" 으로 보고 지우면
라벨이 빈다.**

taxonomy 45종 중 9종은 색인에 곡이 없어 `map_genre` 가 빈 값을 낸다. **실패가 아니라
"아직 곡 없음"** 이다.

### 그 밖에

- **`@EmbeddedId` + 관계가 같은 컬럼을 각자 매핑하면 INSERT 가 터진다**
  (`No value specified for parameter N`). 읽기는 되므로 그 표에 쓴 적이 없으면 안 드러난다.
  `MusicGenre` · `MusicMood` · `MusicSectionAnalysisMood` · `MusicAnalysisInstrument`
  넷 다 그 모양이었고 `@MapsId` 로 고쳤다. **새 매핑 엔티티를 만들면 같은 함정을 본다**
- **`BootstrapRunner` 의 `CodeSeed` 는 `key()` 로 비교한다.** `displayName` 을
  `equals` 에 넣으면 **표시명만 고쳐도 "없는 코드" 로 판정돼 재INSERT → UNIQUE 위반으로
  기동이 실패한다.** 고칠 때 조심한다
- **관리자 API 는 관리자를 위한 것이다.** 배치에 관리자 권한을 주지 않고,
  `/api/v1/admin/**` 을 배치에 열지 않는다. 배치가 필요한 것은 `@SystemRole` 로 따로 낸다
- **운영 pod 은 JupyterHub 에 직접 접근하지 않는다.** 데이터는 `music_preprocessing` 이
  API 로 올린다
- ClickHouse 는 **2샤드**다. `X_local`(Replicated) + `X`(Distributed), DDL 은 `ON CLUSTER mupid_all`
- 변경한 검증·가드는 **일부러 깨뜨려 테스트가 잡는지 확인**한다. 이번에도 그러다
  빈 테스트 하나를 찾았다
