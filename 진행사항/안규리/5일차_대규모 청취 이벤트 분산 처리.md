# 대규모 청취 이벤트 분산 처리

**학습 일자** 2026-08-28

## 이 주제를 고른 이유

사용자 한 명이 음악을 들으면 PLAY, SEEK, SKIP 같은 이벤트가 계속 쌓인다. 사용자가 늘어나면 음원 수보다 청취 이벤트 수가 더 빠르게 증가한다. 이 데이터를 이용해 Listening DNA를 갱신하려면 사용자 이벤트와 음원 특징을 반복해서 결합하고 집계해야 한다.

오늘은 단일 처리의 한계를 확인하고 분산 처리 효과를 검증하는 방법을 알아보았다.

## 처리할 데이터 흐름

```text
원본 User Event
-> 중복 및 오류 제거
-> Session 단위 정리
-> Track·Moment Feature와 Join
-> 사용자별 집계
-> Listening DNA 저장
-> 추천 점수 갱신
```

원본 이벤트는 수정하기보다 계속 추가하는 형태로 저장한다. 정제 규칙이 바뀌어도 원본부터 다시 계산할 수 있어야 한다.

파일 형식은 CSV보다 Parquet이 적합하다. 필요한 열만 읽을 수 있고 압축 효율도 좋다. 날짜별로 파티션을 나누면 특정 기간의 이벤트만 읽기 쉽다. 사용자 ID처럼 값의 종류가 많은 열을 디렉터리 파티션으로 사용하면 작은 파일이 늘어날 수 있으므로 피한다.

## Batch와 Streaming

Listening DNA를 매일 또는 몇 시간마다 갱신한다면 Batch 처리로도 충분하다. 반면 사용자의 행동을 바로 다음 추천에 반영해야 한다면 Streaming 처리가 필요하다.

3주 MVP에서는 다음 순서가 현실적이다.

1. Batch 작업으로 전체 추천 흐름을 완성한다.
2. 처리 시간과 갱신 주기를 측정한다.
3. 지연이 서비스 요구사항을 넘을 때 Streaming 적용을 검토한다.

Spark Structured Streaming은 들어오는 데이터를 연속적인 테이블처럼 다룰 수 있다. 기존 DataFrame 연산과 비슷한 방식으로 집계할 수 있지만, 상태를 오래 유지하는 연산은 메모리 사용량을 확인해야 한다.

## 분산 처리에서 생기는 병목

Spark를 사용한다고 항상 빨라지는 것은 아니다. 데이터 이동이 많으면 단일 처리보다 느릴 수도 있다.

- `groupBy(user_id)` 과정에서 Shuffle이 발생한다.
- 이벤트와 음원 특징을 Join할 때 네트워크 전송이 늘어난다.
- 특정 사용자나 인기곡에 데이터가 몰리면 일부 작업만 오래 걸린다.
- 작은 파일이 많으면 파일을 여는 비용이 커진다.
- Worker 수가 많아질수록 스케줄링 비용도 늘어난다.

음원 특징 테이블이 충분히 작다면 Broadcast Join으로 큰 이벤트 테이블의 이동을 줄일 수 있다. 파티션 수는 고정값으로 정하기보다 데이터 크기와 실행 결과를 보고 조정해야 한다.

## 검증 방법

먼저 Python 또는 단일 Spark Worker로 기준 시간을 측정한다. 그다음 같은 데이터와 같은 집계 조건으로 Worker 수를 늘려 비교한다.

| 이벤트 수 | 단일 처리 | 분산 처리 | 비교 항목 |
|---:|---:|---:|---|
| 100K | 측정 | 측정 | 작은 데이터의 추가 비용 |
| 1M | 측정 | 측정 | 처리량 변화 |
| 10M | 측정 | 측정 | Shuffle과 메모리 사용량 |
| 100M | 측정 | 측정 | 확장 가능 여부 |

기록할 값은 다음과 같다.

- 전체 처리 시간
- 초당 처리 이벤트 수
- Join과 Aggregation에 걸린 시간
- CPU와 메모리 사용량
- Shuffle Read/Write 크기
- Worker 증가에 따른 속도 향상 비율

Spark Web UI에서 Stage별 실행 시간과 Shuffle 크기를 확인하면 어느 연산이 오래 걸리는지 찾을 수 있다.

## 프로젝트에 적용한다면

실제 팀 사용 로그에서 Session 길이, Skip 비율, Replay 빈도 같은 분포를 구한다. 이 분포를 바탕으로 Synthetic Event를 만들고 사용자 수만 늘려 처리량을 비교한다.

Synthetic Event는 실제 사용자 수를 주장하기 위한 자료가 아니다. 데이터 규모가 커질 때 어느 지점부터 분산 처리가 이득인지 확인하는 실험 데이터로 사용해야 한다.

결과에는 가장 빠른 수치만 적기보다 데이터 크기, Worker 수, 파티션 수, 실행 환경을 함께 남겨야 다시 비교할 수 있다.
